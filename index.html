Twilio Flex WhatsApp Hub and spoke One Flex · many WABAs

Running multiple WhatsApp Business Accounts through one Flex instance

This guide is for companies that use one Flex contact center across several WhatsApp Business Accounts. Each WABA keeps its own Twilio subaccount, sender and templates, while agents work from the same Flex desktop.

What this setup provides

  • One agent desktop for several brands or regions
  • Separate senders and templates for each WABA
  • Several ways to assign an outbound sender
  • Spoke-level control over senders, templates and traffic

Account model

The Flex account handles agent work and routing. Each subaccount handles WhatsApp traffic for one WABA. Every task and message keeps a reference to the WABA it belongs to.

Why this needs a custom integration: the standard Flex WhatsApp setup works within one account. A backend service is needed to call the correct subaccount, and the Flex plugin needs to show the sender and templates for the WABA attached to the task.

Operating model

One agent desktop, separate WhatsApp accounts

Flex provides the shared agent experience. The senders, templates and account configuration remain in the subaccount that owns each WABA.

1

Shared Flex desktop

Agents can handle several brands in Flex. The plugin shows which business and sender are active on the task.

N

Add WABAs one at a time

A new WABA is added as another subaccount entry. The Flex environment does not need to be copied.

A sender can be fixed by team, selected from business data, chosen by the agent, or assigned using a mix of these rules.

Implementation paths

Component-level message flow

The account diagram above shows where things live. This view follows the calls made for inbound messages, agent replies, template use and delivery updates.

Flex work and history

How a message becomes work in Flex

The WhatsApp message lives in the subaccount. The agent sees a copy in a Conversation in the Flex account. The Interaction connects that Conversation to Flex, and the TaskRouter task sends the work to an agent.

1 · WhatsApp message

Receive or send

The subaccount creates a Message SID and, for outbound messages, sends delivery updates. Keep the wabaId with them.

2 · Flex history

Add it to a Conversation

Create or reuse the Conversation in the Flex account, make sure the customer is represented and add the message once.

3 · Agent work

Route it through Flex

If no task is active for this thread, link the Conversation to an Interaction and route a task with the WABA details.

4 · Later messages

End the task, keep the history

When the agent finishes, keep the Conversation mapping. A later inbound message can create new work without losing the transcript.

SituationWhat happensWhat to watch
First inbound messageCreate the Conversation and customer representation in the Flex account, add the message, then create the Interaction using that Conversation.The Interaction is created asynchronously. Keep the work pending until its channel and task are ready.
New outbound conversationChoose and lock the WABA, create the Conversation and Flex work, then send through the matching subaccount and add the message to the transcript.Do not enable sending until the WABA is authorized and the thread mapping exists.
Message while a task is activeAdd it once to the existing Conversation and show it to the active agent.Do not create another task for the same open thread.
Message after a task endedIf the business thread is still open, reuse the Conversation and create new agent work.Keep only one active Interaction and task for that thread.
Business thread is closedStart a new Conversation for later contact and link it to the old one if the business needs that reference.Define what closes a thread instead of relying only on TaskRouter status.
Transfer to another agentKeep the same WABA and Conversation and use the chosen Flex transfer or routing process.A transfer must not introduce a second WhatsApp sender.
Routing failures: decide what to do when a workflow times out or a task is cancelled or deleted. Re-route it, close it or flag it for follow-up so the Conversation is not left open with nobody looking after it.

Data contracts

Keep the same IDs from WhatsApp through to Flex

The registry says which subaccount owns each WABA. Conversation mappings keep track of the Flex work, and message mappings connect the Flex transcript to the message sent or received by the subaccount. Credentials stay in the backend.

RecordKeep at leastHow to use it
WABA registrywabaId, display name, account reference, sender address, credential reference, policy reference, languages and statusKeep wabaId stable even if the phone number or credentials change.
Conversation mappingmappingId, wabaId, customer address, thread key, Conversation SID, active Interaction and Task SIDs, status and timestampsAllow only one active work mapping for the same business thread.
Message mappingwabaId, subaccount Message SID, Flex message SID, direction, status, error code, idempotency key and timestampsUse the subaccount and Message SID together. Status callbacks may be repeated or arrive out of order.
Template referencewabaId, Content SID, language, name, approval status, variables and last checked timeUse the Content SID together with the owning account. Template names may be duplicated.

What to put on the Flex task

Keep task attributes small. Include the WABA, the Flex Conversation and the details the agent needs to see. Keep account and credential references in the backend.

  • Do not change wabaId after the thread starts.
  • Use selectionSource to show how it was chosen.
  • Keep policyVersion so the choice can be explained later.
  • Use conversationSid to find the agent-visible history.

Sender assignment

How the system chooses a WABA

Different companies assign senders in different ways. The backend can support these options through one resolver API. It returns the WABAs the agent may use, the default choice and the rule that produced it.

Team mapping

Fixed by queue

Map a team, queue or workflow to one WABA. The agent does not choose a sender.

Useful when teams serve one brand
Business rule

Based on customer context

Use the brand, market, CRM account, campaign, language or a previous conversation.

Useful when the data already identifies the brand
Agent choice

Selected in Flex

Show the agent a list containing only the WABAs they are allowed to use.

Useful for shared service teams
Default + override

Suggested, then confirmed

Choose a default from the available context and let an authorized agent change it before sending.

Useful when most cases are predictable
Once a conversation starts: its WABA and sender remain fixed. If another WABA needs to contact the customer, create a separate conversation and retain a reference to the original interaction.

Inbound messages

Use the destination number to identify the WABA

For an inbound message, the WABA is already known from the webhook route and the WhatsApp number that received it.

01

Receive and verify

The WhatsApp sender calls the webhook configured in its subaccount. Resolve the account from the trusted route and validate X-Twilio-Signature before using the payload.

02

Use one message format

Create a common event with wabaId, sender, customer address, Message SID, body and media references. Use the account and Message SID to spot retries.

03

Find or create the Flex Conversation

Resolve the open mapping using WABA, customer and thread key. For first contact, create the Conversation in the Flex account and its customer representation before routing work.

04

Add the message to Flex

Add the inbound message once to the Flex Conversation. Retrieve media with the owning subaccount's credentials and follow the agreed storage rules.

05

Route it when an agent is needed

If the thread has no active task, create an Interaction using the Conversation and route a task with the WABA details. Wait for setup to finish before showing the work as ready.

06

Show it in Flex

The plugin shows the business and sender. The transcript comes from the Flex Conversation, and replies remain on the same WABA.

Outbound messages

Choose the WABA before loading templates

An outbound message needs a sender before the system can check the 24-hour window or list templates. Both are specific to a WABA.

01

Send the available context

The plugin sends the agent, team, queue, customer, brand, language and previous-conversation data to the WABA resolver.

02

Get the allowed WABAs

The resolver returns the WABAs this agent may use and, where possible, a default. The agent can only choose from that list.

03

Lock the WABA and thread

For new contact, create the Flex Conversation and mapping before enabling send. For an existing thread, verify that the requested WABA matches its fixed context.

04

Check the 24-hour window

Look up the last verified inbound message for this customer and WABA. Allow free-form text inside the window. Outside it, require an approved template.

05

Load templates

Read templates from the selected subaccount. Keep the language, approval status, subaccount and ContentSid with each result. An optional lookup layer may be added for scale.

06

Send from the backend

Check authorization again, record the send request, load the subaccount credentials and call the Messaging API. Save the Message SID before reporting success to Flex.

07

Add it to the transcript

Add the agent's message to the Flex Conversation once. Use validated status callbacks to keep its delivery state up to date.

If a send times out: do not send it again automatically. First check whether Twilio created the message.

WhatsApp templates

Keep templates in the subaccount that owns them

Templates are created and approved in each WABA's subaccount. Flex can present them in one picker, but each template keeps its original subaccount and Content SID.

Baseline

Read from the subaccount

Fetch templates from the owning subaccount when the agent opens the message composer.

  • Always reads the source of truth
  • A good place to start
Only if needed: add a short-lived lookup layer later if direct template reads become too slow. The subaccount remains the source of truth.

Access and credentials

Keep credentials in the backend

Flex only needs the active WABA and the sender details agents should see. The backend resolves credential material that is valid for the subaccount that owns that WABA.

Account-specific context

Each subaccount has its own Account SID and Auth Token context. API keys are created separately and belong to the account where they are created.

Webhook verification

Validate Twilio signatures using the correct account context. Resolve that context from a trusted endpoint mapping, not an untrusted form field.

Agent authorization

Enforce WABA eligibility again in the backend. Hiding a sender in the plugin is useful UX, not an authorization boundary.

Minimal Flex data

Keep task attributes to the routing identifiers and display fields Flex needs. Do not include secrets, tokens or unnecessary customer data.

An account and an API key are not the same thing: a subaccount has its own SID and Auth Token. An API key is created separately and belongs to the account where it was created. Choose the supported authentication method and credential lifecycle that fit the company’s security policy.

Add or remove a WABA

Use the same process for every new WABA

Adding a WABA should be a configuration change, not a plugin change. The plugin reads the new WABA from the registry and sender rules.

Set up the subaccount

Create or choose the Twilio subaccount, complete WhatsApp onboarding, register the sender and confirm it can receive traffic.

Add the templates

Create the templates in that subaccount, wait for approval and note the supported languages and use cases.

Configure the callbacks

Point inbound messages and delivery updates to the correct integration URLs. Test HTTPS and signature validation using this subaccount.

Give the backend access

Register credentials for the subaccount in the backend, keep them behind a credential reference and test the API calls the integration needs.

Add the WABA to the registry

Add the stable wabaId, display name, account, sender, languages and policy reference. Keep it disabled until testing is complete.

Choose who can use it

Set the agents, queues or business rules that may use the WABA. Decide whether it can be suggested automatically and who may change the suggestion.

Test the main paths

Test an inbound message, a reply inside the service window, a template outside it, delivery updates, blocked access and a resumed conversation.

Turn it on

Set the registry entry to active, give the intended teams access and watch routing and delivery for that WABA during rollout.

Removing a WABA: stop it from being selected for new outbound messages first. Let active work finish, then remove callbacks and credentials. Keep or delete the remaining records according to the agreed retention rules.

Acceptance tests

Test the cases that are easy to miss

Run these tests for every WABA in an environment that matches production closely. Save the Message SID, Conversation SID, Interaction SID, Task SID and request ID with the test results.

Go-live checklist

These checks apply no matter how many WABAs are connected or how senders are chosen.

The team agrees how Flex Conversations, Interactions and Tasks are created, closed and resumed.

Every WABA has a stable wabaId mapped to its subaccount and sender, and the task attributes contain no credentials.

Sender rules and override permissions are defined, and the WABA stays fixed after a conversation starts.

Inbound and status webhooks use the correct account context, validate signatures and safely handle duplicates.

The service window is tracked per WABA and customer, and templates come from the owning subaccount.

Credentials stay in the backend and their storage, replacement and revocation are documented.

The acceptance tests pass for every active WABA, and monitoring covers webhook, routing and send errors.

Terms used in this guide

Use the same terms in design documents, task attributes, APIs and support guides.

TermMeaning here

TaskThe TaskRouter work item offered to an agent. It is not the durable conversation history.

Content SIDThe account-qualified identifier for an approved content template used by the owning subaccount.
Service windowThe WhatsApp customer service window in which free-form replies are allowed for that WABA and customer context.
